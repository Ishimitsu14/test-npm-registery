# nestjs-request-context

Данный пакет нужен для использования SCOPE по инициализации провайдеров NestJS.

## Чем не устраивает обычное поведение NestJS?

NestJS из коробки умеет использовать REQUEST Scope для провайдеров. НО есть ряд ограничений, которые признает сама команда NestJS:

- Для каждого запроса создается дерево контекста относительно запроса. Если мы делаем `Inject` внутри singleton-Provider, request-Provider заставляет пересоздавать вверх по дереву каждый Provider, даже если изначально был описан как Singleton. Это влияет на производительность.

Наш пакет позволяет создавать дерево контекста по конкретному запросу

- Мы ограничены инструментарием по управлению и контролю за контекстами, которые создает NestJS. То есть, если мы хотим указать, что конкретный запрос является уникальным, нам нужно использовать express или микросервисы. Других способ работы нет.

Наш пакет позволяет в любой момент создать новый контекст запроса, даже если написали свой Consumer на основе какой-либо библиотки (например, Kafka или BullMQ)

- Есть БОЛЬШАЯ проблема по регистрации SCOPE Provider'ов на уровне Exporer. Например, мы выбрали паттерн CQRS, который предоставляет NestJS.

По правилам, их команды могут быть только Singleton, потому что регистратор предварительно регистрирует эти команды. Если мы сделаем команду как REQUEST Provider, регистратор его не увидит. Часто бывает нужно создавать транзакции на уровне контекста (все что попало в контекст запроса, атомарно записывается в БД). Получается внутри команды нам придется ссылаться на другой REQUEST Provider. Но тогда мы столкнемся с проблемой, описанной в первом пунтке, ведь теперь и команда станет REQUEST Provider. Следовательно, предварительный регистратор команд просто не увидит текущую команду.

## Как использовать?

Везде, где нам надо сделать `Inject` провайдера, который является REQUEST Scope, мы НЕ используем дефолтный (от NestJS) `Inject`.
Вместо этого надо использовать `InjectContext`.

```typescript
export class CommandHandler {
  @InjectContext(UNIT_OF_WORK_INJECTOR)
  private unitOfWork: InjectContext<IUnitOfWork>;

  async execute() {
    const unitOfWork = await this.unitOfWork(); // Resolve в конкретный момент по текущему запросу
  }
}
```

---

В свою очередь сам UnitOfWork является REQUEST Scope, то есть он уникальный для каждого запроса (региструется так же как обычно в NestJS)

```typescript

@Injectable({ scope: Scope.REQUEST })
export class UnitOfWork implements IUnitOfWork, OnModuleInit {
    ...
}
```

## Как задавать контекст на верхнем уровне?

Понятное дело, если мы хотим разделять между собой запросы от разных пользователей, нам надо разделять контексты.
Каждый запрос имеет свой уникальный `ContextId`.

Представим, что у нас есть `KafkaConsumer`, который получает события и мы эти события хотим записать в БД атомарно, и чтобы другие данные не влияли на текущий контекст.

Простой пример:

```typescript

export class KafkaConsumer {
    @Inject(NestContextManager)
    private nestContextManager: NestContextManager;

    ...

    start() {
        this.kafkaClient.consume(this.execute)
    }

    execute(events: Message[]) {
        return this.nestContextManager.runInContext(() => save(events));
    }

}
```

Задавать контекст по запросу лучше описывать в том месте, где принимаются новые запросы. Далее по потоку уже будет контекст запроса, и ни какие данные не повлияют на текущий контекст.

## Защита от дурака

Наш регистратор перед запуском предварительно понимает, правильно ли сделали `Inject`. Если мы случайно заюзаем старый `Inject` для Request scope провайдеров, выйдет исключение (перед запуском приложения). Будет подробно написано, где надо было сделать `InjectContext`
